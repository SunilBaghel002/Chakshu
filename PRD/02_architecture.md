### Layering rules (enforced by import linting)

| Layer | May import | May NOT import |
|---|---|---|
| `api/` | `services/`, `domain/`, `schemas/` | `adapters/` directly, `db` session internals |
| `services/` | `domain/`, `adapters/`, `db/`, `schemas/` | `api/` |
| `domain/` | stdlib, numpy, shapely, rasterio | **anything else.** No FastAPI, no SQLAlchemy, no httpx, no settings |
| `adapters/` | stdlib, httpx, boto3, google-genai | `api/`, `services/` |
| `db/` | SQLAlchemy models, `schemas/` | `api/`, `services/`, `domain/` |

**Why this matters:** `domain/` being pure is what makes the deterministic core testable without a database, network, or fixtures. If you find yourself wanting to import FastAPI into `domain/`, the design is wrong — move the code.

## 3. The two ingestion paths

This is the architectural change driven by the new SIH26167 features. There are now two ways imagery enters the system, and they behave differently.

### Path 1 — Archive ingestion (batch, background)

```
AOI polygon
  → query AWS open-data for Sentinel-2 L2A scenes overlapping it, 2021→present
  → for each month, score candidates by cloud cover (SCL) and pick the best
  → download B02 B03 B04 B08 B11 B12 + SCL as COG
  → reproject to the AOI's UTM zone, cut into 256×256 tiles
  → compute NDVI / NDWI / NDBI per tile
  → embed each tile with CLIP → pgvector
  → INSERT scenes, tiles, tile_vectors
```

Runs as a background job. Pollable via `/api/jobs/{id}`. Idempotent: re-running for the same AOI adds only new months (**A16**).

### Path 2 — User upload (synchronous, seconds)

```
POST /api/uploads  (multipart file)
  → validate: extension, size, magic bytes, band count, dtype
  → open with rasterio
  → ┌─ has CRS + bounds?
    │   YES → georeferenced
    │         derive GSD from the transform
    │         derive acquisition date from metadata, else ask the user
    │         look up the enclosing/nearest AOI
    │         → status = GEOREFERENCED
    │   NO  → not georeferenced
    │         GSD unknown → user must supply it or accept an explicit assumption
    │         no location → no archive comparison possible
    │         → status = VISUAL_ONLY
    └
  → RESOLUTION GATE: classify the image into a capability tier from its GSD
  → run the detection tracks that tier permits
  → INSERT uploads, detections
  → return the Detection set
```

**The capability tier is computed once, stored, and governs everything downstream.** See §5.

**Hash chain:** `entry_hash = sha256(prev_hash || canonical_json(content) || recorded_at)`. Genesis row uses `prev_hash = '0'*64`. A `make verify-audit` target recomputes the whole chain and fails if any link is broken.

**Never** use `UPDATE` on `change_object.status` without also writing a `decision` row. That is what makes the audit meaningful.

## 5. The Resolution Gate ← the most important new component

Everything about detection depends on this. Compute it once at upload, store it, and let it decide what runs.

```python
# domain/resolution.py  — pure function, no I/O

CAPABILITY_TIERS = {
    "T1_VERY_HIGH": {
        "max_gsd_m": 1.0,
        "object_classes": [
            "building",
            "vehicle",
            "aircraft",
            "ship",
            "storage_tank",
            "swimming_pool",
            "tower",
            "container",
            "road",
        ],
        "landcover_classes": ["built", "water", "vegetation", "bare", "crop", "snow"],
        "area_measurements": True,
    },
    "T2_HIGH": {
        "max_gsd_m": 5.0,
        "object_classes": [
            "building",
            "ship",
            "aircraft",
            "storage_tank",
            "tower",
            "road",
        ],
        "landcover_classes": ["built", "water", "vegetation", "bare", "crop", "snow"],
        "area_measurements": True,
    },
    "T3_MEDIUM": {
        "max_gsd_m": 15.0,  # Sentinel-2 lands here
        "object_classes": ["building_cluster", "ship_large", "storage_tank", "road"],
        "landcover_classes": ["built", "water", "vegetation", "bare", "crop", "snow"],
        "area_measurements": True,
    },
    "T4_COARSE": {
        "max_gsd_m": float("inf"),
        "object_classes": [],
        "landcover_classes": ["built", "water", "vegetation", "bare", "crop", "snow"],
        "area_measurements": True,
    },
    "T0_UNKNOWN": {
        "max_gsd_m": None,
        "object_classes": [],
        "landcover_classes": [],
        "area_measurements": False,
    },
}


def resolve_tier(gsd_m: float | None, gsd_source: str | None) -> str: ...
def permitted_labels(tier: str) -> tuple[set[str], set[str]]: ...
```

Behaviour rules:

1. **`gsd_source == 'assumed'` can never yield better than `T3_MEDIUM`.** An assumed resolution is not a basis for a confident detection claim.
2. **`T0_UNKNOWN`** is returned when there is no CRS, no declared GSD, and no user input. In this state the system may still describe the image and answer qualitative questions, but must not draw boxes claiming to be specific object types, and must not report areas in m².
3. When a user asks for something the tier does not permit, the response must **say so explicitly** rather than silently returning nothing. Example message, verbatim:

   > *"This image is 10 m resolution (Sentinel-2). At that scale an individual vehicle is smaller than a single pixel, so I can't count vehicles. I can show you building clusters, roads, water, and land cover. Here's what I found:"*

4. The tier, the GSD, and its source must appear in the execution trace for every answer derived from that upload.

## 6. Detection tracks

Three independent tracks produce `detection` rows. They are allowed to disagree; disagreement is information.

### Track 1 — `landcover_index` (deterministic, preferred)

Requires NIR and SWIR bands. Runs when `band_count >= 4` with the needed bands present.

```
NDWI = (B03 - B08) / (B03 + B08)          water
NDVI = (B08 - B04) / (B08 + B04)          vegetation
NDBI = (B11 - B08) / (B11 + B08)          built-up
NDSI = (B03 - B11) / (B03 + B11)          snow/ice

per pixel, in priority order (first match wins):
  water       if NDWI >  0.15
  snow        if NDSI >  0.40
  vegetation  if NDVI >  0.40
  built       if NDBI >  0.05 and NDVI < 0.25
  crop        if NDVI in [0.20, 0.40] and NDBI < 0.05
  bare        otherwise, if NDVI < 0.20
  → unclassified (no detection row emitted)

then: morphological open (3×3) → connected components → drop < 4 px
     → vectorise → polygon per patch → label = class
score = fraction of constituent pixels meeting the threshold (deterministic, not a model probability)
score_source = 'deterministic'
verified = True
```

These thresholds are **initial values and must be tuned** on the demo sites. Tuning is a task in `build-order.md`; the final values must be written back into this file and into `EVALUATION_REPORT.md`.

### Track 2 — `landcover_worldcover` (deterministic, requires georeferencing)

If `status == GEOREFERENCED`, fetch the overlapping ESA WorldCover 2021 tile (10 m, 11 classes, CC-BY-4.0) and clip it to the image bounds. Emit one polygon per contiguous class patch. `score = 1.0`, `score_source = 'deterministic'`, `verified = True`, and the trace must cite WorldCover as the source — **this is a real map, not our inference.**

Where Track 1 and Track 2 both cover a pixel and disagree, keep both rows and set `score_source = 'agreement'` on neither; instead record the disagreement in the trace. **Do not silently reconcile them.**

### Track 3 — `object_model` (Gemini, the only non-deterministic track)

Runs only when the capability tier permits object classes. This is where hallucination risk is highest, so it is the most heavily guarded.

```
1. Downscale the image so the longest edge ≤ 1568 px. Record the scale factor.
2. Send to Gemini with a strict JSON-schema-constrained prompt (§6.1).
3. Receive: [{label, bbox:[a,b,c,d], score, reason}]
4. VALIDATE every box in domain/bbox.py:
     - all four values finite and within [0, 1000]
     - after normalisation: 0 < x1 < x2 <= width, 0 < y1 < y2 <= height
     - area >= max(16 px², 0.0001 × image area)
     - aspect ratio within [1/12, 12]
     - label ∈ permitted_labels(tier).object_classes   ← hard reject otherwise
     - score >= 0.5
     - deduplicate with NMS at IoU 0.5, keeping the higher score
5. Convert bbox → geom_px (pixel polygon, y down).
6. If GEOREFERENCED: geom_px → geom_4326 via the affine transform; area_m2 via UTM.
   Else: area_m2 = NULL. The UI must show "—" not "0".
7. verified = False, score_source = 'model'
8. Record the raw model output verbatim in the trace, including rejected boxes
   and the reason each was rejected.
```

**The object count displayed to the user is `SELECT count(*) FROM detection WHERE ...`. It is never a number from the model's prose.** This is the §2 rule applied concretely.

### 6.1 The Gemini detection prompt — required properties

- Request **strict JSON only**, no prose, no markdown fences. Use the SDK's structured-output / response-schema feature if available; otherwise validate and reject on parse failure.
- Give the model the GSD and the permitted label list. **Tell it the resolution.** A model that knows it is looking at 10 m pixels will not claim to see cars.
- Ask for a `reason` field per box. Not shown to the user by default; shown in the trace.
- Ask for `score` in [0,1] and instruct that uncertain objects be omitted rather than included at low score.
- Instruct explicitly: *"If an object is smaller than about 3 pixels across at this resolution, do not report it."*
- Include the negative instruction: *"Do not report objects you cannot localise with a box."*

> ⚠️ **VERIFY AT IMPLEMENTATION TIME — do not trust this note blindly.**
> Gemini's bounding-box coordinate convention has differed across model versions (normalised 0–1000, with `[ymin, xmin, ymax, xmax]` ordering in some and `[xmin, ymin, xmax, ymax]` in others). **Read the current API documentation before writing `domain/bbox.py`, and write a test using a synthetic image with a known object at a known position.** Assert the box lands within a tolerance. Do not ship the transform on assumption.

## 7. The question-answering stack

Three tiers, always in this order. Lower tiers are not fallbacks for failure — they are the **default**, and higher tiers are additive polish.

```
user question
   │
   ▼
┌─────────────────────────────────────────────────────────┐
│ TIER 1 — deterministic router  (services/query_router.py)│
│                                                         │
│  1. normalise text (lowercase, strip, expand contractions)│
│  2. regex + keyword extraction: dates, numbers, units,   │
│     class names, comparatives, "how many", "when",       │
│     "bigger than", "in the last N years"                 │
│  3. embed the question with CLIP; cosine-match against   │
│     the intent examples in intents.yml                   │
│  4. pick the highest-scoring intent above threshold 0.72 │
│  5. fill its slots from step 2                           │
│  6. execute the intent's SQL / geometry query            │
│  7. build a MeasurementBundle — every number, with units │
│     and provenance                                       │
│  8. render via templates in render.py                    │
│                                                         │
│  ALWAYS produces a complete answer. No network.          │
└────────────────────────┬────────────────────────────────┘
                         │ MeasurementBundle + question
                         ▼
┌─────────────────────────────────────────────────────────┐
│ TIER 2 — Gemini phrasing  (only when OFFLINE=0 and the   │
│          intent is marked phraseable)                    │
│                                                         │
│  input:  the question, the MeasurementBundle, up to 3    │
│          images (before/mask/after or the upload)        │
│  instruction: rephrase for clarity. DO NOT add, remove,  │
│          or alter any number, date, unit, or class name. │
│          You may not mention anything not in the bundle. │
│  output: candidate prose                                 │
└────────────────────────┬────────────────────────────────┘
                         ▼
┌─────────────────────────────────────────────────────────┐
│ THE NUMBER VERIFIER  (services/verifier.py)              │
│                                                         │
│  1. regex-extract every numeric token, date, and unit    │
│     from the candidate prose                             │
│  2. extract the same from the MeasurementBundle          │
│  3. for each token in the prose, require a match in the  │
│     bundle within tolerance:                             │
│        integers: exact, unless the bundle marks it       │
│                  "approximate" (then ±10%)               │
│        areas/distances: ±2% AND same unit OR a correct   │
│                  conversion (m²↔ha↔km², m↔km)            │
│        dates: exact, or within the stated interval       │
│        percentages: ±1 point                             │
│  4. extract every class name and every named place;      │
│     require presence in the bundle                       │
│  5. VERDICT:                                             │
│       PASS      → use the Gemini prose                   │
│       FAIL      → discard it, use the Tier-1 template,   │
│                   log the diff in the trace, set         │
│                   answer.degraded = true                 │
│                                                         │
│  A FAIL is not an error. It is the system working.       │
│  It must be visible in the trace, never swallowed.       │
└─────────────────────────────────────────────────────────┘
```

**Tier 3 (a full agentic VLM with tool-calling loops) is explicitly out of scope.** Do not build it.

### Intents that must exist

`intents.yml` must define at least these, each with examples, slots, a SQL/geometry handler, and a template:

| Intent | Example utterances | Handler |
|---|---|---|
| `aoi_change_summary` | "what changed here in 3 years" · "changes since 2022" | `services/summary.py` |
| `count_by_type` | "how many buildings" · "count the water bodies" | SQL over `detection` / `change_object` |
| `area_of` | "how big is the new construction" | `measure.py` |
| `onset_of` | "when did it start" · "when was this built" | `onset.py` |
| `locate_class` | "show me the water" · "where are the buildings" | geometry filter → map highlight |
| `filter_changes` | "only bigger than 500 m² after 2024" | SQL predicates |
| `describe_image` | "what is in this image" | Track 1/2/3 aggregate → template |
| `caption_image` | "describe this scene" | Track 1/2 aggregate → template |
| `compare_two_dates` | "compare June 2022 and June 2024" | pair selection → change run |
| `explain_suppression` | "why was this rejected" · "what did you filter out" | `suppress.py` reasons |
| `explain_confidence` | "why only 60%?" | `confidence_parts` |
| `similar_tiles` | "find more like this" | vector kNN |
| `unsupported` | anything below threshold | honest refusal + suggestion |

`unsupported` is a real intent and must produce a real message: *"I can't answer that from the data I have. I can tell you about changes in this area, counts and sizes of what's detected, when a change started, or show you a class on the map. Try one of those."* **Never let the router fall through to a model to paper over a gap it should have declared.**

## 8. Cross-cutting concerns

### Configuration
One `settings.py` using pydantic-settings, reading `.env`. Every variable has a default and a docstring. Key flags:

| Variable | Meaning |
|---|---|
| `OFFLINE` | `1` = no outbound HTTP whatsoever. Adapters must raise `OfflineError` immediately. |
| `GEMINI_ENABLED` | `1` = Tier 2 active. Implies `OFFLINE=0`. |
| `GEMINI_MODEL` | Model id. Pinned, never "latest". |
| `UPLOAD_MAX_MB_GEO` / `UPLOAD_MAX_MB_RGB` | 500 / 25 |
| `CLIP_MODEL` | `ViT-B-32` default. |
| `TINYCD_ENABLED` | `0` by default. Optional corroborator. |
| `DETECTION_SCORE_MIN` | `0.5` |
| `DETECTION_NMS_IOU` | `0.5` |

### Errors
One envelope, everywhere:

```json
{"error": {"code": "RESOLUTION_INSUFFICIENT",
           "message": "human-readable, actionable",
           "details": {},
           "trace_id": "..."}}
```

The full code list is in `data-contracts.md` §6. **Never return a bare 500 with a stack trace to the browser.** Never return an empty array where an explanatory error belongs.

### Long jobs
Anything over ~2 s uses the job pattern: `POST` returns `202 {"job_id": ...}`; `GET /api/jobs/{id}` returns `{state, progress, result?, error?}`. Ingestion, whole-AOI change runs, and batch detection use this. **No WebSockets in this build.**

### Caching
Derived artefacts are written to `data/cache/` keyed by `sha256(inputs)`. Change runs, embeddings, rendered tiles, and detection results are all cached. On demo day everything must be pre-warmed — see `build-order.md` Phase 7.

### Tracing
`services/trace.py` records, for every request that touches the AI stack: the intent matched and its score, the slots extracted, the SQL executed, the MeasurementBundle produced, the tier used, the raw model request and response, the verifier verdict and diff, and every rejection with its reason. Persisted per answer, retrievable via `GET /api/ask/{id}/trace`, rendered by `TracePanel`.

**SIH26167 explicitly requires an auditable execution trace with task, model/tool names, parameters, and outputs. This module is that requirement.** Note that internal reasoning is *not* evaluated — so log what was done, not why the model felt like doing it.

### Testing gates (CI, and run locally via `make check`)
1. `ruff check` and `ruff format --check`
2. `mypy --strict` on `backend/app`
3. `pytest tests/unit` — must not touch DB or network
4. **import-purity check:** assert no module under `domain/` imports `fastapi`, `sqlalchemy`, `httpx`, `google`, or `settings`
5. `pytest tests/integration`
6. `pytest -m offline` with `OFFLINE=1`
7. `tsc --noEmit` and `eslint` on the frontend
8. golden-file diff on API responses — a change here must be deliberate and reviewed
9. `make verify-audit`

## 10. Architecture decisions and their rationale

| Decision | Why | What we rejected |
|---|---|---|
| pgvector inside the same Postgres as PostGIS | Queries are inherently hybrid: vector kNN constrained by AOI geometry, date, sensor, usability. One SQL statement with predicates applied **before** the HNSW scan beats retrieve-then-filter on both speed and precision. HNSW inserts without rebuild → satisfies incremental ingestion directly. | Milvus, Qdrant, Redis, Elasticsearch — all add an operational component for no capability gain |
| Classical index-differencing as the **primary** change detector | Transparent, tunable in an afternoon, licence-free, works on Day 1, and its reasoning is a rule trace a judge can read. | Leading with a pretrained net: LEVIR/SECOND-trained models face a severe domain gap at 10 m over India. Published cross-domain retention is 57–94%, and on realistic multimodal scenes unsupervised methods fall from 70–85% F1 to ~20%. |
| TinyCD as an optional **corroborator** behind a flag | 0.285 M params, runs on CPU in seconds. Where it agrees with classical, confidence rises; where it disagrees, that is a visible caveat. | Making it primary, or training anything |
| Rule table for change classification, not a classifier | SIH26227 §2.2.2 names a closed set of change types. A decision table over ΔNDVI/ΔNDWI/ΔNDBI + SCL + WorldCover is deterministic, millisecond-fast, and emits a `rule_trace` — which *is* the required processing history. | Training a classifier with no labelled Indian data |
| Three detection tracks that may disagree | Track 1 and 2 are trustworthy but coarse; Track 3 is detailed but unreliable. Keeping them separate lets the UI show provenance per label, and lets disagreement become a signal. | Fusing them into one output and losing the provenance |
| The Resolution Gate as a stored, first-class field | It converts "the model guessed wrong" into "we told the user what this resolution can support." That is the difference between a system that hallucinates and one that declares limits. | Letting each feature decide ad hoc |
| Tier-1 router as the default, Gemini as polish | The finale requires offline operation, CPU-only rules out a local VLM at demo speed, and SIH26227 never asks for language generation. | A VLM-first design that cannot run at the finale |
| The Number Verifier as a hard gate, not a warning | It is the only mechanism that makes the core promise (§2) enforceable rather than aspirational. | Trusting the model, or asking it nicely in the prompt |
| Filesystem for blobs, not S3/MinIO | Single machine, demo scale, and MinIO is another container to babysit. Paths are stored in the DB so a later swap is a config change. | Object storage services |
| No background worker (Celery/RQ) | FastAPI `BackgroundTasks` plus a `job` table is sufficient at this scale and removes a Redis dependency and a whole class of failure. | Celery, RQ, Dramatiq |
